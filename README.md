# QASwarm — QA Requirements, Task & Test Design System

Мультиагентная система, которая преобразует подтверждённые требования из Confluence
в задачи Jira и тестовую модель Qase. Управляет процессом агент-оркестратор:
он запускает специалистов, проверяет Quality Gates и формирует итоговый статус.

## Что делает система

Пайплайн из пяти этапов:

| # | Этап | Агент | Результат |
| - | ---- | ----- | --------- |
| 1 | Ревью требований | `requirements-analyst` | `artifacts/requirement-review/v<N>_<YYMMDD_HHMM>.md` |
| 2 | Проектирование задач Jira | `task-designer` | `artifacts/jira-tasks/v<N>_<YYMMDD_HHMM>.md` |
| 3 | Проектирование тестовой модели | `test-designer` | `artifacts/test-model/v<N>_<YYMMDD_HHMM>.md` |
| 4 | Создание задач в Jira | `jira-publisher` | `artifacts/jira-creation/<spec-file-stem>.md` + ключи |
| 5 | Создание сущностей в Qase | `qase-publisher` | `artifacts/qase-creation/<spec-file-stem>.md` + ID |

Этапы 2 и 3 независимы и запускаются параллельно, как и этапы 4 и 5.
Каждый этап заканчивается проверкой Quality Gate. Ни один этап не выполняется
в обход Gate, а `SUCCESS` невозможен, пока хотя бы один обязательный этап не завершён фактически.

Любой неразрешённый конфликт требований останавливает Workflow после ревью с
`REQUIRES_HUMAN_DECISION` и конкретным запросом решения человеку. Дизайнеры и паблишеры
не запускаются — даже для незатронутых требований. `FINAL` у Review означает полноту
анализа, а не согласованность требований; Readiness явно фиксирует запрет дизайна и ID
блокировок. Блокирующие вопросы также требуют решения до продолжения.

## Архитектура

- **Оркестратор** (`orchestrator`) — единая точка входа. Ведёт Workflow, маршрутизирует
  этапы, читает проектные значения (Jira/Qase, read-only), проверяет Gates. Прав записи
  в Jira и Qase не имеет.
- **Специалисты-проектировщики** (`requirements-analyst`, `task-designer`, `test-designer`) —
  работают только на чтение, создают промежуточные artifacts.
- **Паблишеры** (`jira-publisher`, `qase-publisher`) — единственные агенты с правом записи,
  создают сущности строго по проверенной спецификации и фиксируют ответы Tool в Creation Report.

Общий контракт всех агентов — `AGENTS.md`. Роли — `.opencode/agents/*.md`.
Методики этапов — `.opencode/skills/<skill-id>/SKILL.md`.

## Предварительные условия

- Установлен [OpenCode](https://opencode.ai).
- Подключен Qase через MCP-сервер (`qase`).
- Подключена Jira через MCP-сервер.
- Заданы переменные окружения для Confluence:

  | Переменная | Назначение |
  | ---------- | ---------- |
  | `CONFLUENCE_URL` | Базовый URL Confluence |
  | `CONFLUENCE_EMAIL` / `CONFLUENCE_TOKEN` | Учётные данные Confluence |

Переменные окружения задаются через переменные системы, либо указать в `..\.secrets\confluence.json` пользователя.

Структура документа:
```json
{
    "email":  "email@gmail.com",
    "url":  "https://example.atlassian.net",
    "token":  "CONFLUENCE_TOKEN"
}
```

### Настройка моделей агентов

Перед запуском необходимо предварительно указать в `opencode.jsonc` проекта модели,
которые используют агенты. Без корректно настроенных моделей агенты не смогут быть
запущены. Модель задаётся в двух местах:

- **Глобально** — ключ `model` верхнего уровня задаёт модель по умолчанию для всех агентов:

  ```jsonc
  "model": "tokenharbor/deepseek-v4.1-flash",
  ```

- **Для конкретного агента** — в блоке `agents` переопределяется отдельным ключом `model`.
  Паблишеры обычно выносятся на менее мощную модель:

  ```jsonc
  "agents": {
    "requirements-analyst": { "model": "tokenharbor/deepseek-v4.1-flash" },
    "task-designer":        { "model": "tokenharbor/deepseek-v4.1-flash" },
    "test-designer":        { "model": "tokenharbor/deepseek-v4.1-flash" },
    "jira-publisher":       { "model": "nvidia/nemotron-3-ultra-550b-a55b:free" },
    "qase-publisher":       { "model": "nvidia/nemotron-3-ultra-550b-a55b:free" }
  }
  ```

Формат значения — `providerID/modelID`. Значения в примере соответствуют текущей
конфигурации проекта; при смене провайдера или модели укажите актуальные идентификаторы
(их можно посмотреть в списке доступных моделей OpenCode). 

## Запуск

Проектная конфигурация `.opencode` подхватывается автоматически при старте OpenCode
в каталоге проекта. Агент по умолчанию — `orchestrator` (см. `opencode.jsonc`).

После старта активна роль `orchestrator`. Отдельных скриптов запуска нет — работа
начинается с постановки задачи оркестратору в диалоге.

### Обязательные входные данные

Соберите их до запуска (или ответьте на вопросы оркестратора):

- **Confluence** — `pageId` страницы с требованиями. Если дан URL, `pageId` извлекается
  из него (поиска по страницам нет, только чтение по ID).
- **Jira** — site / `cloudId` и ключ проекта.
- **Qase** — код проекта.
- **Ограничения запуска** — что именно нужно сделать: полный цикл или отдельные этапы.

Если чего-то не хватает, оркестратор вернёт `REQUIRES_HUMAN_DECISION` с точным перечнем
недостающего. Предположениями пробелы не заполняются.

### Проектные значения (опционально)

Проектные значения — тип задачи, обязательные поля, допустимые типы связей и их направление,
дерево сюит и их ID, custom fields, числовые ID значений `priority`/`type` и т.п.

- Их можно **опционально передать** прямо при постановке задачи. Переданные значения
  воспринимаются как факты и используются как есть.
- Если они **не переданы**, оркестратор определит их **автоматически** read-only вызовами
  (`getJiraProjectIssueTypesMetadata`, `getJiraIssueTypeMetaWithFields`, `getIssueLinkTypes`,
  `qase_project_context` и т.д.) и передаст субагентам.
- Перебор и «пробные» сущности для выяснения схемы полей запрещены: если значение нельзя
  получить чтением — оркестратор вернёт `REQUIRES_HUMAN_DECISION` с перечнем недостающих.

### Пример задачи оркестратору

```
Запусти полный цикл.
Требования: <URL Confluence с pageId=...>
Jira-проект: PROJ
Qase-проект: DEMO
Нужны и задачи Jira, и тестовая модель Qase.
```

Проектные значения можно не указывать — оркестратор определит их автоматически. При желании
их можно задать явно прямо в задаче:

```
Тип задачи Jira: Task
Обязательные поля: ...
Тип связи: Blocks (inward: is blocked by)
```

Оркестратор сам определит версии артефактов, выяснит (или примет переданные) проектные
значения и запустит этапы в правильном порядке.

## Управление версиями артефактов

- Артефакты хранятся как `artifacts/<artifact_name>/v<N>_<YYMMDD_HHMM>.md`, где `N` — целое число версии, `YYMMDD_HHMM` — метка времени создания (локальное время окружения), например `v3_261107_1430.md`.
- Номер новой версии = максимальный существующий + 1. Назначает оркестратор вместе с полным путём.
- Метку времени назначает оркестратор; после создания имя файла не меняется.
- Существующая версия никогда не перезаписывается: правки — это новая версия.
- Исключение — Creation Report: его имя совпадает с именем исполняемой спецификации без расширения (`v<N>_<YYMMDD_HHMM>.md`).
- Каждый артефакт начинается с обязательной шапки (`Версия`, `Producer`, `Consumer`,
  `Входные artifacts`, `Дата`, `Статус`). `DRAFT` означает, что Gate пройти нельзя.

## Возобновление после сбоя

`jira-publisher` и `qase-publisher` создают по одному файлу отчёта на версию спецификации:
`artifacts/jira-creation/<spec-file-stem>.md` и `artifacts/qase-creation/<spec-file-stem>.md`.
Отчёт — это ledger и точка возобновления. Правила:

- файл создаётся первым действием паблишера и далее **дополняется на месте**;
- повторный запуск по той же спецификации продолжает тот же файл (новый файл отчёта
  и новая метка времени не создаются);
- `CREATED` не создаётся повторно, `FAILED` — одна повторная попытка, `PENDING` — создаётся;
- перед созданием выполняется pre-flight поиск по устойчивому идентификатору (Jira: проект +
  summary + тип; Qase: проект + тип + заголовок/сюита), а не только по отчёту; найденная
  сущность записывается с пометкой «найдено при возобновлении»;
- при потерянном ответе Tool сначала выполняется reconciliation-поиск, затем одна повторная
  попытка, только если сущность не найдена.

Чтобы возобновить прерванный прогон, попросите оркестратора перезапустить паблишер
с тем же путём отчёта и `resume: yes`.

## Неинтерактивные eval: fresh / resume

Обычный интерактивный запуск выше **не меняется**: `run_type`, run_id и параметры
eval-контейнеров вводить не нужно. Агент по умолчанию остаётся `orchestrator`.

Для eval тип задаётся только в `evals/dataset/golden_dataset.json`:

```json
{
"input": {
  "source": "confluence",
  "page_id": 3964929,
  "run_type": "fresh"
}
}
```

- **`fresh`** — заново читает и анализирует Confluence; только после пройденных Gates
  без блокировок создаёт новый Epic Jira и корневую suite Qase с общим run_id
  (время + UUID). Все задачи/кейсы находятся
  внутри этих контейнеров; проверка дублей ограничена их пространством на всех этапах.
- **`resume`** — продолжает последний зарегистрированный fresh той же страницы
  и тех же проектов, включая частично завершённый. Сохраняет run_id, контейнеры,
  спецификации и Creation Report; завершённые сущности не создаёт повторно.
  Если fresh отсутствует, повреждён или требования изменились, происходит явная
  блокировка, а не автоматический переход к fresh.
- Конфликт Review блокирует и `fresh`, и `resume`: при неинтерактивном запуске
  запрос с ID и источниками возвращается в итоговом ответе, а не заменяется разрешением
  на частичную публикацию. При остановке до дизайна Epic/suite и спецификации не создаются.
- Существующие shared steps Qase можно переиспользовать без namespace, если их
  содержание совпадает со спецификацией. Они фиксируются как `SKIPPED` с ID/hash,
  проверяются чтением и не изменяются.

Команда запуска:

```powershell
python evals/eval_runner.py --debug
```

Runner проверяет `run_type` и передаёт его в служебный `EVAL_CONTEXT`. Соседние
кейсы с одинаковыми pageId/type оценивают один запуск; смена страницы или типа
создаёт отдельный запуск. Порядок dataset сохраняется, поэтому последовательность
`fresh → resume → fresh` не объединяется в один ответ.

Промпт передаётся через stdin из сохранённого UTF-8-файла.
Первое действие оркестратора — проверка переданного manifest; неполный eval-контекст
блокирует запуск.

До fresh создаётся `artifacts/eval-runs/<pageId>/<run_id>.json`. Оркестратор
записывает в него пути, проектные факты и подтверждённые checkpoints; runner ведёт
журнал попыток. Последний fresh определяется по времени начала, не обновлению
отчёта. ОС-блокировка сериализует весь eval в проекте, включая оценку judge, и
освобождается при завершении процесса. Старые артефакты и сущности автоматически
не удаляются.

Промпт, полная stdout-трасса каждой попытки и ответ сохраняются в
`evals/results/runs/<run_id>/attempt-<N>.prompt.md`, `attempt-<N>.jsonl` и
`attempt-<N>.response.md`, в том числе без `--debug`. Evaluator использует
отдельную скрытую read-only роль
`eval-judge`, получает режим и пути текущих доказательств. Он не запускает Workflow,
а итоговый PASS/FAIL вычисляется из результатов всех проверяемых пунктов.
Для resume ему доступны трассы предыдущих попыток только этого же run_id.
Gates и существующие правила подтверждения публикации не отменяются.

До judge runner проверяет техническую полноту eval handoff: итоговый статус должен
быть зарегистрирован оркестратором в manifest, а для `SUCCESS` нужны текущие файлы
доказательств, идентификаторы обоих контейнеров и все обязательные Gates `PASSED`.
Это проверка непротиворечивости handoff, не Quality Gate и не доказательство
корректной публикации; Gates по-прежнему устанавливает только оркестратор. Отсутствующий
handoff даёт `ERROR`, даже при коде процесса 0. Завершённую с кодом 0 попытку без
зарегистрированного handoff нельзя автоматически продолжить через `resume`.

`--format json` кодирует поток событий OpenCode, а не только ответ модели.
Evaluator разбирает только итоговое сообщение; промежуточные реплики не склеиваются
с ним. Принимается один JSON-объект строго по схеме: текст вокруг JSON, Markdown,
повторяющиеся ключи, `NaN`/`Infinity` и неверные поля дают `ERROR`, без ремонта ответа.

Скрипты внутри используют частный процесс OpenCode (`--standalone`): при ошибке
чтения или Ctrl+C останавливается только собственное дерево процессов, а частичный
ответ сохраняется. Общий интерактивный сервис не останавливается. Если остановку
подтвердить нельзя, следующие запуски dataset не выполняются.

Локальные проверки без вызовов Jira/Qase/Confluence:

```powershell
python -m unittest discover -s evals/tests -v
```

## Структура репозитория

```
.
├─ AGENTS.md                 # общий контракт всех агентов
├─ opencode.jsonc            # конфигурация OpenCode: агенты, модели, права
├─ README.md
├─ .opencode/
│  ├─ agents/                # роли: orchestrator, *-designer, *-publisher
│  ├─ skills/                # методики этапов (requirement-review, task-design, test-design)
│  └─ plugins/
├─ evals/                    # runner, evaluator, golden dataset и локальные тесты
└─ artifacts/
   ├─ requirement-review/    # этап 1
   ├─ jira-tasks/            # этап 2 (спецификация)
   ├─ test-model/            # этап 3 (спецификация)
   ├─ jira-creation/         # этап 4 (отчёт создания)
   ├─ qase-creation/         # этап 5 (отчёт создания)
   └─ eval-runs/             # manifest только неинтерактивных eval
```

## Статусы

Итоговый статус Workflow:

| Статус | Значение |
| ------ | -------- |
| `SUCCESS` | все обязательные этапы завершены и подтверждены |
| `PARTIAL` | часть независимых операций выполнена |
| `FAILED` | операция или этап провалены |
| `REQUIRES_HUMAN_DECISION` | нужно решение владельца требований |

Статус Creation Report (`IN_PROGRESS` / `COMPLETE` / `PARTIAL` / `FAILED`) — отдельный
словарь и на итоговый статус Workflow не переносится.

## Безопасность и границы прав

- Паблишеры создают новые сущности. Если независимый Publication Gate находит расхождение
  со спецификацией, тот же паблишер может точечно обновить только сущность, созданную текущим
  Workflow и зафиксированную в его Creation Report. После update оркестратор повторно проверяет
  только исправленные сущности; удаление и смена статусов по-прежнему запрещены.
- Автоматический rollback через удаление запрещён: частичный результат фиксируется как `PARTIAL`.
- Сущности «для проверки» схемы полей («пробные», «минимальные») запрещены — значения
  выясняются чтением, иначе фиксируется блокировка.
- Права ограничены технически через `permissions` в `opencode.jsonc` и ролях.
  Отказ в правах — граница дизайна: фиксируется блокировка и эскалируется.
- Роли и инструкции правит только агент `build` по явному указанию владельца; оркестратор
  и специалисты прав на запись в `AGENTS.md`, `opencode.jsonc` и `.opencode/*` не имеют.
- Перед публикацией оркестратор запрашивает у человека подтверждение с перечнем создаваемых
  сущностей; без подтверждения задачи Jira и тест-кейсы Qase не создаются.

## Диагностика

| Симптом | Что делать |
| ------- | ---------- |
| `REQUIRES_HUMAN_DECISION` | Ответьте на указанные вопросы требований либо дозаполните входные данные/проектные значения; конфликт требует нового Review и повторного Gate до дизайна |
| Требования недоступны | Проверьте `CONFLUENCE_URL`, креды и корректность `pageId` |
| Gate не пройден | Оркестратор вернёт задачу тому же агенту (не более 2 циклов), затем эскалирует зависимый этап |
| Создание оборвалось | Перезапустите паблишер с тем же отчётом и `resume: yes` |
| Нет прав в Jira/Qase | Проверьте доступ к проекту и переменные окружения; права агента не обходятся |
